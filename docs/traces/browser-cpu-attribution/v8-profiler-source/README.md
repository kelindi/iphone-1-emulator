# Does plain CDP CPU profiling force WebAssembly tier-up?

**The reviewed V8 15.2.124.21 path does not force WebAssembly tier-up merely because `Profiler.start` or code logging is enabled.** It does enable sampling, code-event logging and JavaScript profiling bookkeeping, so this is not a claim of zero profiler overhead. No new browser or guest run was used for this source review.

The V8 version reported by Chrome152 in our traces resolves to commit `4323497a6a73839e6d5260f6acd7ec0212cb3321`. [Revision metadata](revision.json) and [all fetched source URLs/SHA-256 values](sources.json) pin the review. Source files remain local under `.context/v8-profiler-review`; the manifest allows exact retrieval without copying a large external source tree into this repository.

## Plain profiling call path

1. The inspector's enable handler only records its enabled state. Starting a profile creates a CPU profiler, applies the sampling interval and starts recording. There is no debugger-enable, debugger-disable or WebAssembly compilation request in these handlers. [Profiler agent, lines225,284,465](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/inspector/v8-profiler-agent-impl.cc#225).
2. The public CPU-profiler constructor forwards to the internal profiler; its default logging policy is lazy. Starting the sampling processor installs the profiling scope and logger. [Public defaults](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/include/v8-profiler.h#436), [constructor and start path](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/profiler/cpu-profiler.cc#539).
3. The profiling scope sets profiling state, enables WebAssembly code logging and enumerates existing compiled code. Its sampling processor is separate from compilation workers. [Scope and processor](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/profiler/cpu-profiler.cc#75).
4. WebAssembly code logging changes per-isolate/per-module logging flags and a module-count bookkeeping field. The module flag is an atomic boolean. Logging existing module code iterates the owned code already present. These paths do not enqueue compilation or alter tier selection. [Engine logging](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/wasm/wasm-engine.cc#1432), [flag setter](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/wasm/wasm-code-manager.h#886), [existing code enumeration](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/wasm/wasm-code-manager.cc#1097).
5. Normal lazy tier selection still uses the module's debug state and ordinary compiler/tiering flags; the lazy compile path logs newly compiled code when logging is enabled. Logging is not its compile trigger. Explicit all-function tier-up exists as a distinct operation, absent from the reviewed profiling path. [Tier selection](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/wasm/module-compiler.cc#975), [lazy compilation](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/wasm/module-compiler.cc#1105), [explicit all-function operation](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/wasm/module-compiler.cc#4177).

Profiling state is not inert: it collects JavaScript bytecode source positions, requests invalidation of the no-profiling protector and updates code-relocation bookkeeping. This can affect JavaScript/API paths and incurs setup/logging/sampling cost. It is not an explicit force-all-Wasm-tier-up request. [State setter](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/execution/isolate.h#1535), [protector invalidation](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/execution/isolate.cc#2620).

## Debugger state is a separate path

The [V8 pipeline overview](https://v8.dev/docs/wasm-compilation-pipeline#profiling) describes recording in the DevTools Performance UI in a debugging workflow. That prose should not be extended into a claim that every plain CDP sampling request forces all Wasm functions to compile.

In this pinned source, debugger enable explicitly enters WebAssembly debugging and removes non-debug code. Debugger disable leaves that state and removes debug code when no isolate still needs it; removing debug code allows later top-tier jobs again. This is a separate state transition from the profiler handlers above. The exact current DevTools frontend orchestration was not audited here, so this review does not assert every detail of that UI workflow. [Debugger enable/disable](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/inspector/v8-debugger.cc#103), [engine transitions](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/wasm/wasm-engine.cc#816), [debug-code removal and re-arming](https://chromium.googlesource.com/v8/v8/+/4323497a6a73839e6d5260f6acd7ec0212cb3321/src/wasm/wasm-code-manager.cc#2851).

## Consequence for the retained measurements

The original CPU attribution collector enables only the Profiler domain during measured stages. Its debugger-based bytecode retrieval is called in final cleanup after sampling ends; both requests time out and remain documented. The later first-use collector never calls that retrieval method: it starts tracing before navigation, uses ordinary Profiler sampling per stage and closes tracing afterward. Its categories are V8/Wasm/detailed compilation, not a command to the DevTools Performance UI. [CPU collector](../profile-browser.mjs), [first-use collector](../../browser-first-use/run.mjs), [shared CDP methods](../../browser-first-use/cdp.mjs).

Therefore no observed blanket Wasm tier-up is explained by the plain profiler/logging call chain reviewed here. The compilation events remain valid observations **under profiling**, with normal observer overhead. This does not prove their exact magnitude is unchanged without profiling, bind anonymous top-tier events to a particular module, establish a causal savings percentage, or repair the separately retained strict screenshot failures. Those original limits remain in force.
