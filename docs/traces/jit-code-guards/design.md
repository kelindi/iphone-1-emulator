# Proposed raw-code guard census (no policy change)

Status: source-only design. Run only after the separate Thumb POP browser decision, using whichever seed is then accepted. The existing static.json is an unweighted layout inventory and cannot estimate actual workload savings.

Use the exact production runtime, current MBX Settings fixture and original compiler/input for the accepted seed. Add only diagnostic writes into a separately allocated bounded counter buffer; retain every raw opcode check, its order, every branch, budget check, fallback and stale callback. Keep the instrumented source and generated seed hashes. Never compare its wall time with production: the counters deliberately add work.

Count at each existing raw-check site: attempted check, mismatched check, checks for instruction addresses before the current block entry PC, and checks at/after entry. Count block arrivals by block length and entry offset. Separately count instructions that pass the existing budget check and begin their generated body, and successful retirements. This distinction matters because a memory guard may fall back after an instruction begins but before retirement. Use a local entry-PC value captured before the block checks, not r15 after execution. Do not add JS callbacks per check; bounded 64-bit counters in host scratch memory avoid an unbounded trace or per-check JS transition.

The aggregate number of raw checks divided by body starts gives measured checking intensity, not the speed improvement from another policy. Earlier-prefix checks are definitely unexecuted at that entry. Later checked words might execute, might be skipped by an exact budget, or might follow a memory fallback; do not label them removable from an aggregate total alone. A bounded per-block length/entry-offset histogram and per-instruction starts can identify where a precise next experiment is warranted.

Replay interpreter, uninstrumented seed, and instrumented seed through the same fixed 100M input sequence. Require complete raw snapshots at the checkpoint, positive generated execution, and exact generated/call/region counters between the two seeds. Prove unchanged admissions and uninstrumented compiler bodies except inserted counter statements. Counter totals must reconcile with the block histogram and stale exits. Scratch counters and pointers must never enter guest RAM or serialized state.

If a later experiment moves checks immediately after each instruction's budget check, it changes invalidation policy even when architectural execution remains equivalent. Test changed earlier prefixes on a tail entry, changed unexecuted suffixes, changes to the next instruction, stale exits after prior generated work, branches and page crossings, zero and exact budgets, and guest stores through physical code aliases. Compare architectural execution explicitly; generated-call/retirement counts can legitimately differ and must not be claimed identical without proof. No guard relaxation or implementation is authorized by this design alone.
