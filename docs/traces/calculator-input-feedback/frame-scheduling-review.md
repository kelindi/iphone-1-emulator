# Independent Calculator audit and frame-scheduling review

The source and retained second run agree on 60 measurements: 30 alternating 9 and C presses, correct expected 9/0 values, every final confirmation within 2 RGB/exactalpha, six required served hashes, and positive generated execution. Nearest-rank p95 uses observation 29 of 30. Button p95 is 165.4/165.6ms; signed release-to-result p95 is 134.5/134.4ms. The conservative declared 150ms button-observation gate therefore fails. No threshold is relaxed. The original first-warmup BigInt serialization failure remains separate; no unfavorable latency dataset was repeated.

`independent-audit.py` re-derives timestamps, earliest qualifying samples, all per-key statistics, sample order/count and strict reported comparisons; eight altered-report negatives reject. Individual raw crops were not saved for every press, so this is an independent source/log audit, not a fresh recomputation of all 60 pixel arrays. The original image references are separately hashed by the executed browser code.

## Cadence limits the causal conclusion

Every one of 60 button detections occurs on the first observed changed guest frame after pointerdown. There is no observed unchanged post-down frame bounding highlight onset. Among 210 within-press intervals between recorded new-frame observations, the median is 42.8ms, p95 83.3ms and maximum 100.2ms. In 162 intervals, canvas sequence advances by 2–4, proving that at least one actual canvas update was skipped by the observer. Those intervals are not all requestAnimationFrame callbacks: the test records only callbacks seeing a new sequence.

The production app writes incoming guest pixels immediately in its worker message handler (`web/app.js`, frame branch), sets the sequence and returns the transferable buffer. It does not wait for requestAnimationFrame. The test's next animation-frame observation can therefore occur after the true canvas write. The roughly 15.6ms p95 overage is smaller than the retained observation cadence. It remains a failed conservative observation gate; it does not establish that the actual canvas response, physical display or guest execution exceeded 150ms.

Pulse lengths are 30.5–33.0ms (median 31.9ms). All retained `savedAt` values are 0. The production 30s autosave timer remains enabled, but its 2s idle guard prevents normal saves during the sub-second repeated presses; no completed autosave overlap is observed. Do not imply this is a Save-latency test.

## Concrete source opportunities, not established causes

`web/emu-worker.js` runs approximately 6ms CPU slices, then checks whether at least 16.667ms has elapsed since `lastFrame`. Assigning `lastFrame = now` after a due attempt moves the next deadline to the end of that slice. It can lower effective presentation-check frequency through repeated slice quantization. The same assignment occurs if `present()` returns immediately because its sole transferable frame buffer is still owned by the page. Recycling merely restores the buffer; it does not schedule a missed presentation.

A bounded potential change is to preserve a fixed presentation deadline and avoid consuming a presentation opportunity while no buffer is available. It would retain the existing single-buffer backpressure, immediate canvas write, actual guest framebuffer, guest clock, instruction/device budgets and input protocol. It must never advance guest time merely to present. However, this run records neither presentation attempts nor worker buffer availability; it cannot quantify how often either source path mattered. There is no justified optimization or predicted latency saving yet. Extra framebuffer scans can consume CPU and regress navigation.

The next useful measurement is an isolated harness receipt on every actual worker frame message, after the unchanged production canvas handler, recording the sequence and same-page clock before the same independent pixel comparisons. Preserve the existing RAF observation alongside it to measure the observation delay directly. No frame-message handling, buffer ownership, guest input, source clock or renderer policy should change. This distinguishes actual canvas arrival from RAF sampling before modifying the scheduler. Only if actual arrival still misses the target and a bounded worker attempt/buffer receipt attributes a material portion to deferred presentation should the fixed-deadline candidate proceed to fake-clock/backpressure/paused/restore and real exact-screen/guest-state gates, then one separately coordinated comparison.

No browser, guest, compilation or production mutation was performed for this review.
