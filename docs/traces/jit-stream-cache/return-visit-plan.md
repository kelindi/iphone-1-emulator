# Proposed return-visit comparison — not run or promoted

The isolated two-session mechanism gate proves persistent accepted seed native-code reuse, with all eight strict phone screens passing. It used one-hour HTTP freshness and explicit service-worker bypass. Before a product speed claim, test realistic validation headers and distinguish first Settings on return from ordinary guest-warm navigation.

1. Freeze two identical b3237/d9c661 phone sites, original loader versus the verified streaming candidate only. Use separate stable loopback origins, one isolated server each, both configured `Cache-Control: no-cache` plus the same SHA-derived strong ETag and correct304 responses. Never change files/URL mid-arm; pin every dependency, fixture, Chrome executable, harness and references. Keep service workers explicitly bypassed for this HTTP gate; actual CacheStorage/offline validation remains separate. One-hour freshness on a mutable production seed URL is not proposed.
2. Create two initially empty persistent profiles, one per loader. Train each once with identical paused normal Import, all 512 regions installed, fixed1-second delay after Resume, and exactly two Settings/Home cycles. Pause after fixed work, wait10seconds for normal serialization, retain traces and uncut recording, then close each entire browser process tree. The original training session also freezes independent settled C0/H1 screen references under the validation phase below, before any measured arm runs. Do not train until a desired result appears. Baseline performs the same guest work even though its binary compilation path does not populate streaming native-code cache.
3. In the agreed quiet window, run four fresh Chrome processes in **original → candidate → candidate → original** order, reusing only the corresponding profile. Before each resumed phone, trace startup only to obtain cache receipts; import the same guest while paused, confirm all 512 regions, finish/drain that trace while paused, then Resume with the same fixed 1-second delay. No Profiler/Debugger or Playwright routing; no extra seed fetch for hashing. A candidate that cannot demonstrate accepted reuse under no-cache/304 has failed this header gate; do not silently switch back to max-age.
4. Each measured return session performs 11 Settings/Home cycles with maintained input/readiness rules and normal30-second Save behavior. The first Settings/Home pair is reported separately (two observations per configuration); rounds2–11 give 20 guest-warm observations per action/configuration. Keep all orders, save overlap, counter deltas, errors and frames. Do not call two first-return samples p95, and do not mix them with warm-app samples. Both candidate measured visits and both baseline visits have the same numbered training/return history, though the second visit may naturally add cached code from the first; record that explicitly.
5. Record each full session without cuts or speed changes. For this new benchmark only, move the existing1-second inter-action idle before validation capture. Capture the matching screen PNG. This50ms confirmation is fixed, not a retry-until-matching loop. Initial release-to-readiness latency is recorded before that validation wait and remains unchanged; no validation time is included in it. All 88 stage validations retain full content, without a scrollbar crop or wider tolerance. Manually review first Settings/Home per session and every failed frame. Require positive generated work, exact initial imported guest cycles/ticks and complete Chrome process closure; capture native cache URL/digest/success nesting before timed navigation.

Training can run as a functional preflight before the coordinated quiet four-session timing window; the header/cache receipt result must be reviewed before claiming timing acceptance.

A useful outcome is a repeatable first-return benefit in both paired directions without a warm Settings/Home regression or correctness failures. Even then the small first-return sample count needs explicit limits. Full production promotion separately requires the real service-worker CacheStorage path, introduction of the changed loader/offline bundle, preserved existing phone saves, missing/bad asset fallback and no-cache/ETag deployment compatibility. First-ever launch has no native code cache; no benefit there is assumed.
