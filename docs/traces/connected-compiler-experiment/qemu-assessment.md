# QEMU-WASM integration feasibility — source assessment

Date: 2026-09-06. Pinned fork: `ktock/qemu-wasm@0ef7b4e2814b231705d8371dd7997f5b72e70baf`.

**Decision:** credible ARM1176 system-engine reuse candidate, but not a replacement function accepting our `arm_cpu_t`/`arm_bus_t`. The lowest-coupling route keeps QEMU CPU state, ARM MMU, TCG and memory infrastructure, and bridges our existing physical devices, interrupts, deadline scheduler and saved-state format. This need not rewrite every device. Extracting just the WASM backend while keeping our CPU/MMU is a separate compiler integration project, not a small binding layer. Neither route has demonstrated speed or iPhone compatibility.

Only 15 targeted files were downloaded, totaling 1,116,868 bytes; exact URLs/SHA-256/lengths are in [qemu-source/manifest.json](qemu-source/manifest.json). No clone, build, guest execution or product changes. Source presence is not tested conformance.

## Actual ARMv6 support

The pinned [target/arm/tcg/cpu32.c](https://github.com/ktock/qemu-wasm/blob/0ef7b4e2814b231705d8371dd7997f5b72e70baf/target/arm/tcg/cpu32.c#L276) registers `arm1176`, MIDR `0x410fb767`, V6K, VAPA, cache-related features, VFP identification and reset CP15 values. This is stronger evidence than the README's AArch64 Raspberry Pi example, but does not prove Apple's CPU-specific identification/coprocessor behavior matches.

[target/arm/ptw.c](https://github.com/ktock/qemu-wasm/blob/0ef7b4e2814b231705d8371dd7997f5b72e70baf/target/arm/ptw.c#L1047) implements `get_phys_addr_v6`, including descriptor/domain/AP/execute-permission handling. [tlb_helper.c](https://github.com/ktock/qemu-wasm/blob/0ef7b4e2814b231705d8371dd7997f5b72e70baf/target/arm/tcg/tlb_helper.c#L298) connects architectural translation to QEMU TLB fills and restores instruction state before delivering a translation fault. This is a full-system path, not user-mode address translation.

## WASM backend constraints

The actual pinned [wasm32.h](https://github.com/ktock/qemu-wasm/blob/0ef7b4e2814b231705d8371dd7997f5b72e70baf/tcg/wasm32.h#L40) threshold is **1500**, correcting the README's illustrative “e.g. 1000.” [wasm32.c](https://github.com/ktock/qemu-wasm/blob/0ef7b4e2814b231705d8371dd7997f5b72e70baf/tcg/wasm32.c) uses synchronous `WebAssembly.Module`/`Instance`, imported shared memory/helper functions and growing function-table entries. `wasmContext` carries a `CPUArchState*`, TCI continuation and unwind state. The implementation caps live instances at 15,000, evicts entries and tracks garbage collection; it can yield under instance pressure. Thus module compilation, eviction and async unwind/runtime requirements remain real costs, not an already solved low-latency browser package.

The [README](https://github.com/ktock/qemu-wasm/blob/0ef7b4e2814b231705d8371dd7997f5b72e70baf/README.md) build uses pthread/shared memory, table growth, Asyncify and QEMU/Emscripten support libraries. Its 2300MB example memory setting is not established as a minimum; it must not be copied as a proven requirement. At this pin the project labels itself experimental and distinguishes upstream TCI from the proposed JIT. Existing browser support/deployment constraints and original 512 seed ABI are not automatically preserved.

## Scope decision and smallest meaningful qualification

**Preferred if pursuing reuse:** an isolated QEMU ARM1176 system harness owning its CPU/MMU, with RAM and a small MMIO/IRQ bridge. Before a whole phone port, qualify explicit architectural fixtures: banked/CPSR/CP15/VFP state conversion; mapped/permission-faulting/cross-page accesses; physical aliases and CPU/DMA code writes; exact budget/IRQ/WFI boundaries. Then run an actual retained phone interval with the existing devices. Compare architectural state and device events, not QEMU internal counters to our JIT counters. Existing known WASM VFP defects make baseline equality alone insufficient for floating-point conformance.

**If preserving our CPU/MMU is mandatory:** reuse selected implementation ideas, or deliberately build a TCG-compatible IR producer plus helper/state/softMMU adapters. The existing ARM translator cannot be detached by changing its top-level pointer type. This loses much of the benefit of reusing QEMU's architectural semantics and requires fresh optimizer/compiler correctness proof.

Recommendation: retain QEMU as a substantial alternative architecture with a clear qualification boundary, not the immediate bounded optimization. Do not promise a speedup or reject it from interpreter-only performance. Root's connected-region prototype in the existing engine has a much smaller compatibility surface; its measured result should inform whether a QEMU integration investment is justified.
