# Source feasibility after first-use attribution

These are bounded proposals, not implemented optimizations. Neither reopens a parked micro-optimization. The first-use trace identifies real compilation, but ordinary warm guest execution remains several seconds; both must be evaluated separately.

## Steady execution priority: continue across already admitted region targets

`core/src/soc/machine.c` currently tries generated execution, then calls `arm_step` once whenever budget remains, even if the generated function returned solely because the PC crossed its one-KiB region boundary. The original MBX census contains 3,209,650 such crossings per 100M retired instructions. Original admission masks permit 2,601,329 target entries, or 81.05%; region presence alone gives the misleadingly broader 91.42%. This is a count ceiling, not an expected wall-time saving. Budget-limited crossings and uncached/faulting fetches reduce the eligible subset further.

The existing `arm_fetch_cache_try_refill` in `core/src/mmu.c` is a useful narrow primitive. It accepts only an already valid fetch cache, MMU-off RAM, or a successful matching FETCH TLB entry with the current complete MMU stamp, privilege, tag and generation. It never walks page tables or accepts a cached fault. It changes the fetch cache and counts a TLB hit only after full RAM backing is confirmed. This avoids inventing a second translation cache or relaxing fetch permissions. The helper exists in origin/main; whether an unused copy survives production dead-code removal is irrelevant to an isolated relink that explicitly calls it.

A bounded candidate can loop inside `arm_wasm_jit_try` after a positive generated prefix only when PC/mode has crossed to a different region, the destination entry is admitted, and this exact refill succeeds. Each next function receives only the original remaining instruction budget. Existing exception/IRQ/FIQ/mode/alignment and generated raw-code/physical-alias guards remain mandatory. A zero-progress or unsupported/memory/fault exit returns to the existing interpreter path immediately; no spinning retry. No recursive generated calls or extra device time is allowed. Original seed bodies and ABI can remain unchanged.

First measure eligible successful refills and remaining budgets using the current frozen MBX workload. That is a cost-ranking census, not a performance claim. Its upper bound is only about 2.6M forced fallback instructions, under 10% of the original 26.9M interpreted instructions; their translation/dispatch cost may differ from average. The earlier `arm_step` 29.09%, fused `emu_run` 12.22% and `region_find` 6.37% samples identify containing work, not the fraction this candidate can remove. A positive prototype needs exact architectural/full-state replay, explicit changed JIT accounting, fetch-hit/miss/fault/XN/privilege/stamp/wrap cases, stale-code and physical-alias cases, and budgets immediately before device/interrupt boundaries before quiet timing.

## First-use candidate: split large generated bodies into lazy internal groups

The measured lazy-baseline cost is concrete: C0 Settings compiles 226 seed function bodies totaling 5.65 MB, versus only 20.6 KB of newly touched core bodies. Current `tools/jit/compiler.cjs:compileRegion` places every admitted basic block from one KiB of guest code into one exported WASM function, with a whole-region dispatch loop and a shared register-local set. Its existing 64-basic-block groups limit dispatch nesting but are still part of the same host function. Touching one entry therefore lazily compiles the whole body, including paths not yet visited.

A separate candidate could retain all 512 public region exports/admission masks while moving bounded groups (for example at most 32 basic blocks) into internal WASM functions. A small public dispatcher selects the internal group by current PC and invokes another group only after a committed cross-group transition with remaining budget. Each group retains the same block raw-code checks, tail entry behavior, flags and writeback. Budget, page/mode, stale-code and unsupported exits return immediately as before. No guest instruction is pre-executed to warm the browser, and startup is not delayed by a mandatory warmup.

The potential saving is that an unvisited group remains uncompiled and each compiled host function is smaller. The tradeoff is more internal calls/register spills on hot cross-group edges and possibly more total module bytes. Anonymous top-tier trace events do not prove which large body dominates optimizing compilation, so there is no numerical top-tier saving prediction. This candidate must remain separate from region continuation. First compare compiled body-size/work distributions and exact state; then compare real first-use compilation plus warm Settings/Home so reduced startup cost cannot conceal a steady-state regression. The original 32 MB asset cap, 512 installed table-slot cap and optional-startup/fallback lifecycle remain in force.

The steady continuation candidate is the preferred next execution experiment because it keeps the original seed and its now-measured first-use cost unchanged. The internal-group design is a concrete first-use alternative if continuation's eligible-cost census is too small. Neither has promotion approval or a claimed gain.
