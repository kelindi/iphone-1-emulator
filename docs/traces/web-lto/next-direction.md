# Next direction after LTO: find repeated guest routines across both engines

No new optimization is justified by the existing host profiles alone. The strongest larger direction is to identify repeated, semantically bounded guest routines—such as copying/filling or another tight data-processing loop—across **both** interpreted and generated execution, before considering an emulator-side loop fast path. This is a hypothesis about where a larger improvement could come from, not evidence that memcpy dominates. No guest binary patch, build, profiling run or optimization was made for this note.

The accepted warm Settings profile has3,660ms emulator-worker scheduler CPU in a3,657ms stage (snapshot boundaries/clock granularity explain the slight excess), with only1.96% sampled idle. Its largest exclusive sampled groups are arm_step29.09%, generated code28.07%, fused emu_run12.22%, memory/MMU/bus11.83% and region_find6.37%. Named MBX0.84%, frame1.85%, other device/clock1.15% and observed emscripten_get_now23.298ms do not justify a new rendering or host-clock-frequency rewrite. Inlined work stays unresolved, and this603679 profile predates later save/classifier changes; it is directional evidence, not current per-function timing. [Accepted attribution](../browser-cpu-attribution/analysis.json).

The original seed handles the bulk of retired instructions while still consuming roughly28% of worker residency. The all-fallback census records only interpreter steps; it cannot identify total routine work including generated instructions. The older copy/fill inventory had only region call counts, which likewise cannot show executed loop iterations. Expanding64 pages/2,048 bits, register omission, guard relocation, continuation, POP, decoder rearrangement, lazy groups and now LTO are parked for measured reasons. A further source rearrangement or small coverage increment would repeat the same unsupported extrapolation.

A read-only recomputation of the retained warm Settings table also rules out a tempting misreading: its7,416,861 admission=4 interpreter steps are **not**7.4M zero-return generated failures. Actual provenance totals are12,986,461 missing-region attempts;5,071,566 missing-bit attempts;9,746,937 mandatory steps after positive generated prefixes;2,053,346 runtime-guard rejections;352,235 generated-zero cases; and7 no-attempt steps. The zero-return reason remains unknown. Do not call all admitted fallbacks memory-cache misses or reopen parked caches from that number. [Raw census](../jit-fallback-census/browser/warm-settings-rows.json.gz), [provenance definitions](../jit-fallback-census/source/census.h).

A bounded next measurement, if authorized, would extend the already proven count-only census with committed **generated basic-block/entry counts**, keyed to the exact existing512 seed and pinned instruction bytes. Combine those with actual interpreter PC/opcode counts for one warm Settings window and Home control. The aim is a complete executed-PC/routine inventory that can falsify a bulk-loop hypothesis, not a new speed number. Entry-at-tail, short budgets, branches, condition failures, stale guards, memory refusal and partial positive prefixes must credit only actually retired generated instructions. Preserve all architectural/raw snapshot bytes and original JIT policy counters in deterministic preflight; bounded table overflow must reject, and the original observation failures stay retained. Guest routine attribution must bind to actual loaded bytes/symbols and preserve unknown/aliased mappings.

Only if a small set of original routines accounts for a material fraction of **all** Settings execution should a narrow signature-guarded bulk implementation be proposed. It would have to preserve faults and partial commits, register/flags/PC, code/data aliases, MMIO refusal, actual memory accounting, interrupts and the unchanged remaining device budget. A copy/fill signature by itself is not a shortcut license. If execution is diffuse or no such routine exists, reject this direction before an implementation. Current evidence gives no honest expected millisecond saving and does not establish that this alone can reach two seconds.
