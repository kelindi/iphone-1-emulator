# Isolated full-web LLVM LTO candidate

Production is unchanged. Source is a copied 111-file C/header/CMake projection of the exact released RTC source tree; all copied files match current production source. Rebuild target **emu only** into isolated control/candidate dist directories. The `jit_seed ALL` and `offline_bundle ALL` targets are never invoked. No generated seed, ABI, application, manifest or service worker is rewritten.

No prior web LTO experiment was found in the retained speed plans or durable CPU evidence. The existing native build enables CMake IPO only under NOT IPHONE1_WEB. Released web compile/link receipts contain -O3 and no -flto. This differs from parked generated-register omission, guard movement, Thumb POP, dispatch continuation and coverage changes: only LLVM's cross-translation-unit optimization policy changes.

Pinned Emscripten is 4.0.16, commit 09534bba7f0ee767bf6f6f8cb5b7bf9519b8d63a. Its local docs/emcc.txt specifies -flto as a compile-and-link option. The [official WebAssembly guide](https://emscripten.org/docs/compiling/WebAssembly.html) recommends ordinary LTO rather than less-tested ThinLTO; the [optimization guide](https://emscripten.org/docs/optimizing/Optimizing-Code.html) requires the option at compile and link. Candidate sets only CMAKE_C_FLAGS=-flto=full, which the actual generated compile and executable link commands both use. SDK system libraries also select their existing LTO variants where supported; some runtime library objects deliberately remain ordinary WASM per the pinned tools/system_libs.py. This is therefore a full-LTO core/API build, not a claim that every SDK object becomes bitcode.

Keep -O3, no fast-math or Ofast, and the original source-specific **VFP -ffp-contract=off**. No relaxed SIMD or other feature flags are enabled. This preserves the intended floating-point compilation policy; focused VFP execution remains a required correctness gate, not something inferred solely from flags.

Before execution, require a full control build byte-identical to released 7a72, a repeat link producing byte-identical candidate WASM/glue, identical original public JS API functions, initial memory and all 16 live JIT ABI offsets/revision 1. Preserve all original 512 seed definitions/admission bits, 512 runtime limit, stale/fault/alias/budget guards and snapshot/accounting semantics. Internal function numbering and memory allocation addresses can change with LTO; they are not treated as stable symbol mappings. Original seed operates through the verified C structure offsets and live memory imports.

## Proposed correctness gate before any timing

1. Run the existing actual-emitter boundary oracle against separately linked control/LTO core with identical source and original compiler. Compare all architectural, RAM, MMU, exception, guard and JIT accounting fields, including stale code, budget boundaries, physical code aliases, invalid spans, interworking and zero-progress fallback. Preserve any first mismatch.
2. Compile and execute the existing focused VFP test as WASM under both compile/link policies. It must retain literal floating-point expected results, rounding/fusion-sensitive cases and status flags. Do not substitute a native-only test for the actual LLVM/WASM candidate.
3. One deterministic 100M pair using the retained genuine MBX Settings fixture and original 512 seed. The control full build must be byte-identical before its retained exact control checkpoints may be reused. Preserve raw snapshots before assertions at 25M/50M/75M/100M, complete frame bytes and all original JIT/TLB/read counters. Candidate interpreter and seeded execution should both match the exact control raw state; positive generated retirement is mandatory for the enabled arm and zero for interpreter. No field normalization is preauthorized.
4. Stop on any unexpected mismatch. No timing/browser, promotion, extra optimization or repeat-to-pass is included in this stage. Only after all gates pass should a separately coordinated fixed-work timing contract be considered. Actual navigation must still justify any eventual promotion.

The mechanism is potential cross-file inlining and optimization of interpreter/MMU/device helpers and API/runtime dispatch. Prior CPU samples identify interpreter/core work as material, but do not predict how much LTO will optimize or whether code growth/compilation effects help Chrome. Binary size is structural evidence only.
