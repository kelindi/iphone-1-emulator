## What a count means

Reuse the accepted interpreter census unchanged: one row records each actual arm_step call's original status, PC/mode and fetched opcode if any, with explicit IRQ/FIQ/prefetch/data-abort flags and actual attempt provenance. ARM_OK means a completed interpreter step; fetched+ARM_OK is not a promise of side-effect commit (condition-failed instructions and abort handling remain distinct limitations). No speculative fetch/MMU read is added.

For generated code, increment a dense u64 counter immediately after the original `n++` for that instruction. A block-entry counter is insufficient: tails, short budgets, conditional branches, guard refusals and positive prefixes can execute only part of a block. Code that branches to the existing exit before n++ receives no generated count. Failed-condition ARM instructions still retire and count, without a side-effect claim. The sum must equal the unchanged generated-retired policy counter delta; then generated counts plus completed interpreter steps must equal machine retirement in the actual machine-loop preflight. The old helper's try-or-fallback semantics are not falsely substituted for mandatory production fallback after a positive prefix.

Index counters by original region index*512 + aligned instruction offset (ARM word offsets, Thumb halfword offsets). 512*512*u64 =2MiB, statically allocated outside guest RAM. Metadata pins each emitted index to its exact virtual PC/mode/opcode and original module/input hash. Unsupported/unemitted slots must remain zero. No hash collisions or generated-row eviction. Each counter saturates at u64max and records overflow; any overflow rejects. The interpreter retains its proven524288-row/20MiB table,64-probe odd-stride hash and explicit overflow/map/lifecycle refusal. Reset/start clears both count sets; stop preserves collected rows. Installs/reset during capture invalidate acceptance. Disabled instrumentation changes only host overhead, never guest behavior.

A generated PC/opcode match does not establish physical page or routine identity. Virtual aliases, remapped identical code and unknown symbol bindings remain explicit; no new translation is performed to fill missing provenance. Changing interpreter opcodes stay separate rows. Guest routine attribution requires actual loaded-byte/image/slide binding; unknown mappings stay unknown. Counts are not CPU-time estimates or measured latency savings.
